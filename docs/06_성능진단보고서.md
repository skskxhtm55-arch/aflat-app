## 2. 측정 결과 (휴대폰, 실측)

"전체" = 휴대폰에서 요청을 보내고 받기까지. "서버" = Apps Script 안에서 처리한 시간. "전체 − 서버" = 통신 + 구글 플랫폼 시간.

| 요청 | 횟수 | 전체 (ms) | 서버 (ms) | 그중 로그인 확인 | 캘린더 |
|---|---|---|---|---|---|
| 내 정보(getMe, 앱 시작) | 1 | 4,151 | 1,587 | 1,397 | - |
| 소식 목록(로그인 확인 없음) | 1 | 2,026 | 804 | 0 | - |
| 내 일정(홈·내 예약) | 4 | 3,916~5,355 | 2,168~3,515 | 1,014~1,607 | 487~683 |
| 시간표(날짜 바꾸기) | 6 | 3,193~6,029 (1회 11,447) | 1,236~4,425 | 1,135~2,736 | 0~777 |
| 예약 확정 | 1 | 7,984 | 5,296 | 2,151 | 307 |
| 예약 변경 | 1 | 10,078 | 8,530 | 1,473 | 2,878 |
| 예약 취소 | 1 | 6,215 | 3,881 | 2,409 | - |

해석
- **로그인 확인(계정·회원 시트 2번 읽기)**: 14회 평균 **1,631ms**. 시간표 요청은 서버 시간의 47~92%가 여기에 쓰임.
  - 시트 자체는 작지만, 요청마다 스프레드시트를 여는 첫 접근 비용이 큼. 소식 목록처럼 시트를 1번만 읽어도 421ms.
- **통신 + 플랫폼 시간**: 대부분 1.5~2.6초. 한 번(시간표 11.4초)은 9초가 통신·플랫폼에서 걸림 → 일시적 지연으로 판단(재현 안 됨).
- **앱 시작**: 내 정보(4.2초)를 받은 **뒤에야** 소식·내 일정(동시, 최대 3.9초)을 요청 → 두 번을 차례로 기다려 8.3초.
- **예약 확정·변경·취소**: 로그인 확인·캘린더 외에도 2.8~4.2초가 더 걸림. 캘린더 일정 만들기·지우기, 예약로그·알림로그 기록(한 줄 쓸 때 칸마다 서식을 따로 지정) 때문으로 **추정**(세부 측정 안 함).
- 같은 날짜 시간표를 1분 안에 다시 볼 때 캘린더 0회 → 서버 기억(캐시)은 잘 동작.

## 3. 개선안 (효과 큰 순)

| # | 개선 | 예상 효과 (추정) | 위험·대응 | 작업량 |
|---|---|---|---|---|
| **P1** | **로그인 확인 결과 기억하기**: 계정·회원 정보를 몇 분간 서버 캐시에 보관. 시간표·내 일정·소식 등 **조회**는 시트를 아예 열지 않게 됨 | 로그인한 요청마다 **약 1~2.5초 단축**. 시간표 날짜 전환 4~6초 → 약 2.5~3.5초 | 회원 시트를 고쳐도(예: 휴원 전환) 최대 5분 늦게 반영 → ① **예약 확정·변경은 시트를 직접 다시 확인**(정확성 유지) ② 시트 메뉴 "설정 즉시 반영"·관리 화면 변경·비밀번호 변경 시 즉시 지움 | 중 |
| **P2** | **앱 시작 기다림 줄이기**: 마지막으로 받은 내 정보·소식·내 일정을 휴대폰에 보관 → 앱을 열면 **바로 표시**하고, 뒤에서 세 가지를 **동시에** 새로 받아 바꿔 끼움 | 홈이 보이기까지 8.3초 → **거의 즉시**(이전 내용), 최신 내용은 약 2.5~4초 | 몇 초간 이전 내용이 보임("업데이트 중" 표시). 로그인이 풀렸으면 새로 받는 순간 로그인 화면으로 | 중 |
| **P3** | **예약 확정·변경·취소 단축**: 기록 한 줄을 한 번에 쓰기, 스프레드시트를 요청당 한 번만 열기, 변경 시 같은 날 일정 재사용 | 각각 약 1~2초 단축 (세부 측정 후 확정) | 낮음 — 기능 변화 없음 | 소 |
| **P4** | **시간표 날짜 전환 기억**: 휴대폰에서 날짜별 결과를 1분간 보관(서버 캐시와 같은 시간) | 이미 본 날짜로 돌아가면 즉시 | 최대 1분 전 현황(지금도 서버가 1분 기억하므로 동일). 예약 확정 시에는 항상 서버가 캘린더 직접 확인 | 소 |

권장하지 않는 것
- 서버를 다른 곳(유료 서버 등)으로 옮기기: "통신+플랫폼 1.5~2.6초"를 줄이는 유일한 방법이지만 **비용 0원 원칙**에 어긋남.
- 화면 파일 압축·글꼴 최적화: 이미 작고 빨라서 체감 효과 거의 없음.
- 캘린더 대신 시트에 예약 현황 복사: **캘린더가 원본** 원칙에 어긋나고 이중 관리 위험.

- 남은 가장 큰 덩어리: 요청마다 드는 통신+플랫폼 시간(1.3~2.3초)과, 앱을 열 때 "내 정보 → 소식·내 일정" 두 번을 차례로 기다리는 구조 → **P2** 대상.

### P3 · P4 · S1~S4 (2026-11-25, 서버 + 화면 v1.6.0) — 재측정 전
- **캘린더 4개 동시 읽기**: 일정 목록을 구글 캘린더 API로 룸 4개 한꺼번에 요청(UrlFetchApp.fetchAll). 일정마다 제목·시각을 따로 꺼내던 시간이 사라짐.
  - 되돌리기: 스크립트 속성 `CAL_READ_MODE = legacy` (코드 수정 없이 예전 방식)
  - 점검: 시트 메뉴 **설치·테스트 도구 → 캘린더 읽기 비교** — 두 방식이 같은 일정을 읽는지와 걸린 시간 비교
  - 캘린더 API가 일시 오류(429·500 등)를 내면 "비어 있음"으로 보지 않고 요청을 실패시킴(잘못된 배정 방지)
  - 사용량: 시간표·내 일정 1번에 외부 호출 4건. 무료 계정 하루 한도 20,000건 → 하루 약 5,000번 조회까지(서버 1분 기억 별도). 현재 규모로 충분할 것으로 **추정**
- **기록 쓰기 한 번에**: 예약로그 여러 줄·글자 서식을 칸마다가 아니라 한 번에 씀
- **시간표 1분 기억(휴대폰)**: 이미 본 날짜로 돌아가면 서버 요청 없이 바로. 예약·변경·취소 후·예약 실패 후에는 새로 받음
- **코드 정리**: 시간표 불러오기 하나로 합침(S3), 예약 화면에서 화면 모양·검사 규칙을 별도 함수로 분리(S2, 192줄 → 본문 162줄 + 도우미 2개), 시각 표시 함수 하나로(S4)
